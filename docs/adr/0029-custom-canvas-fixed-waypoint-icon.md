# ADR-0029: Custom `lv_canvas` icon for the fixed-waypoint status indicator, not an `LV_SYMBOL_*` glyph or image asset

Status: Accepted
Date: 2026-08-07
Decided by: Claude (proposed), you approved (chose the monochrome-dot-and-ring option after seeing
the yellow/orange-colored first pass, and asked for it 50% larger)

## Context

The fixed-waypoint live-distance label (`waypoint_distance_label`) needed a small companion icon —
a second, more visible tap target and a "this is what fixed means" visual cue — placed above it on
the radar HUD. You referenced two visual styles as inspiration (a crosshair/aim reticle, an eye
glyph) and asked whether either was "something included in LVGL, or if it's easy to draw using
LVGL."

Three real options existed:

1. **A built-in `LV_SYMBOL_*` glyph.** LVGL 8.3's symbol font is a fixed FontAwesome subset
   (`lv_symbol_def.h`). Checked directly rather than assumed: there is no crosshair, target, or
   reticle glyph in that set. The two closest are `LV_SYMBOL_GPS` (a location pin — wrong semantics,
   reads as "place a waypoint" not "locked on") and `LV_SYMBOL_EYE_OPEN`/`LV_SYMBOL_EYE_CLOSE`
   (plausible for "watching," but a fixed shape LVGL ships, not something this project can restyle to
   match its own HUD language).
2. **`lv_img` with a pre-converted image asset.** LVGL's image widget needs either a C-array
   generated by LVGL's image converter or a runtime decoder. Grepping the codebase found neither:
   `LV_USE_PNG`/`LV_USE_SJPG`/`LV_USE_GIF` are all `0` (lv_conf defaults, never overridden), and there
   is no `lv_img_create`/`LV_IMG_DECLARE` anywhere in `src/` or `include/` today — no asset pipeline,
   no precedent, no build-time conversion step. Adopting this option for one icon would mean standing
   up that whole pipeline first.
3. **Hand-drawn onto a small `lv_canvas`.** A precedent for exactly this already existed, just never
   ADR'd: `drawBeaconFoundIndicator()` (`navigation.cpp`) draws a circle outline + 5-arm star onto a
   40×40 `TRUE_COLOR_ALPHA` canvas for the beacon-found HUD indicator, with an established
   creation/hide-show/theme-redraw lifecycle (`ui_manager.cpp` creation site, `hideHUD()`, the
   daylight-mode redraw block).

## Decision

Draw the icon by hand onto a dedicated `lv_canvas`, following the `drawBeaconFoundIndicator()`
pattern exactly: a new `drawFixedWaypointIndicator(lv_obj_t* canvas, bool daylight)` function
(`navigation.cpp`) using `lv_canvas_draw_arc` for a ring and `lv_canvas_draw_rect` (with
`LV_RADIUS_CIRCLE`) for a filled center dot — a "locked on" dot-in-ring, not a crosshair or eye.
`ui_manager.cpp` creates the canvas (static buffer, `LV_CANVAS_BUF_SIZE_TRUE_COLOR_ALPHA`), wires the
same tap handler as the distance label, and hides/redraws it at the same call sites
`beacon_found_canvas` already uses.

Two refinements landed the same day from field feedback on the first pass: the icon started
colored (the waypoint's own yellow/dark-orange, matching the on-radar beacon dot) but was changed to
monochrome white/black — matching the rest of the HUD chrome (`waypoint_distance_label`,
`beacon_dbm_label`) — since a status icon reading as "the same color as a map object" was the wrong
signal; and it was sized up 50% (30×30 → 45×45, ring radius 12→18, dot 12px→18px) for legibility.

## Consequences

**Easier**: reuses a widget lifecycle already proven correct (hide/show with HUD, redraw on daylight
toggle, static-buffer allocation) instead of inventing a second pattern — the diff is almost entirely
new content inside an existing shape, not new plumbing. No asset pipeline had to be built.

**Harder / given up**: every future icon on this HUD needs the same hand-drawn treatment — there is
still no image-asset pipeline in this project, so anything genuinely photographic or requiring more
than compass-primitive shapes (arcs, rects, polygons) would hit the same wall this ADR describes and
need its own decision. The icon also costs a small fixed RAM allocation per instance (~6KB at the
final 45×45/`TRUE_COLOR_ALPHA` size — see the CHANGELOG entry for the measured delta) rather than
flash-resident image data, which is fine at this scale (one icon) but wouldn't be free to repeat for
many.

**Retroactive note**: `drawBeaconFoundIndicator()` predates this ADR and was never itself documented
as a decision — this ADR covers the pattern going forward but doesn't backfill that one.
