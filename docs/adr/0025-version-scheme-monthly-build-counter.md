# ADR-0025: `FW_VERSION` changed from `vYY.MM.DD` to `vYY.MM.##` (monthly build counter)

Status: Accepted
Date: 2026-08-06
Decided by: Claude (proposed, you approved)

## Context

`scripts/gen_version.py` (a PlatformIO pre-build extra_script) had written `FW_VERSION` as
`vYY.MM.DD` since it was introduced — see CHANGELOG.md's original "CalVer Versioning + Per-Build
Stamp" entry. That scheme ties the visible version to the calendar day the binary was compiled: it
undercounts on any day with more than one build (a normal occurrence during iteration — this session
alone produced three), and stays static across a whole day of changes, so `FW_VERSION` alone can't
tell two same-day builds apart. (`FW_STAMP_VAL`, the reflash-detection mechanism in
`settings_manager.cpp`, was never affected by this — it's keyed off `FW_BUILD_TS`, a per-build Unix
timestamp, not off `FW_VERSION`.)

Two ways to get a real per-build counter were considered:

- **A separate state file** (e.g. `scripts/.version_state.json`) tracking `{year, month, count}`,
  read and rewritten each build. Simple, but it's a second source of truth alongside the committed
  `fw_version_gen.h` fallback, and it needs its own answer for "what happens on a machine that has
  the header but not the state file" (a fresh clone, or the header regenerated by hand).
- **Parsing the previous build's version back out of the committed `fw_version_gen.h`** — the same
  file the script already overwrites on every build, and which the header's own comment already
  calls a "committed fallback." No new file, and the fallback and the counter's history are
  necessarily the same object, so there's no drift between them to reason about.

## Decision

Use the committed header itself as the counter's persisted state. `gen_version.py` regexes the
previous `FW_VERSION` out of `fw_version_gen.h` before overwriting it; if the parsed year/month
matches the current build's, the counter increments, otherwise (new month, or no parseable previous
version — e.g. first-ever build, or someone hand-edited the fallback) it resets to `01`.

The counter increments on **every** build, not on every meaningful change or every release — matching
how the old `DD` scheme already behaved (it also changed on rebuilds, just only once per calendar
day). `FW_BUILD_TS` and `FW_STAMP_VAL` are untouched.

## Consequences

**Easier**: same-day builds are now distinguishable at a glance on the loading screen and in
`/update`'s current-version banner, without adding a file or a build dependency.

**Harder**: nothing meaningfully — the parse is a single regex against a file whose format the script
itself controls.

**Gave up**: the counter is a build count, not a release count — many values in a busy dev day (this
session alone: `v26.08.01` → `.02` → `.03`) rather than one per shipped version. That trade was
accepted deliberately: a release-only counter would need a second mechanism to distinguish "I'm about
to ship" from "I'm iterating," which nothing in this build currently signals.
